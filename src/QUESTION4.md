# 第四问 · 扰动实验与实时重调度

## 运行

从仓库根目录执行：

```powershell
python -m src.disturbance
python -m unittest -v src.test_disturbance
```

程序读取第二问冻结的 `results/question2/original_plan.json`，将第四问输出写入 `results/question4/`。可用 `--output-dir q4-debug` 指定临时输出目录。

## 实验设计

扰动时刻固定为 5 s。新增告警采用四个固定方位，水平距离为 30、40、50、40 m，高度均为 50 m。单车故障枚举五辆车。主实验将通信恢复时刻设为 10、20、30 s，即中断时长分别为 5、15、25 s。另设时长敏感性组，取 5、17.5、30 s，对应恢复时刻 10、22.5、35 s，并在结果中单独标记。

场景覆盖单项扰动、两两组合和三种扰动组合。合计 209 个固定场景。新增告警、故障车辆和恢复时刻在配对策略间保持相同。

| 策略 | 行为定义 |
|---|---|
| `retain_original` | 回放冻结原计划；新增告警不进入原分配。故障导致双车任务不能执行时，相关健康车按原计划等待。 |
| `skip_failed_task` | 故障敏感性对照。跳过需要故障车的任务，剩余任务沿用原分配、站点和顺序。 |
| `realtime_reschedule` | 在当前车辆状态和允许的信息时点上，重新分配未锁定任务，并联合选择车辆任务顺序与站点。 |

原计划假定在 0 s 已完整下发。因此仅通信中断而没有新任务或故障时，车辆继续执行手头已收到的计划，保留原计划与重调度结果相同是预期现象。通信中断与新增告警、故障组合时，重调度等待恢复后再使用新信息。

同刻规则为先推进到 5 s，再锁定实际启动时刻严格早于 5 s 的观测，然后处理扰动，最后重新判断恰在 5 s 启动的任务。得分窗口为闭区间 `[0, 60]`。窗口内启动任务数决定完成率；任务不全时 `t_last` 记为 60 s。

## 当前结果

本次运行生成 593 条策略结果行。实时重调度在所有场景中均于 60 s 内启动了全部告警。保留原计划的新增告警场景平均完成率为 75%，因为固定原计划不会自动处理新告警。故障场景中，保留原计划和跳过对照平均完成率均为 73.3%；含新增告警和故障的场景平均完成率为 55%。这些结果是当前冻结计划、参数和候选搜索范围下的实验结果。

通信中断单独发生时，保留原计划与实时重调度的结果相同。含故障时，通信恢复时刻较晚会增加部分实时重调度场景的 `t_last`。固定方位新增告警和有限场景样本用于可重复的方案比较，不代表对所有连续方位、距离和高度分布的统计推断。

## 输出文件

| 文件 | 内容 |
|---|---|
| `scenarios.json` | 每个场景的扰动参数、故障车、恢复时刻、中断时长和计分分母。 |
| `scenario_scores.csv` | 场景与策略级成功数、完成率、最晚启动时刻及各告警启动时刻。 |
| `event_log.csv` | 配对策略事件记录，包含车辆、任务、阶段、时间和状态信息。 |
| `aggregate_scores.csv` | 按扰动集合、策略和中断口径汇总的均值、最好值和最差值。 |
| `manifest.json` | 输入计划、源文件和输出文件的 SHA-256，以及运行口径和聚合结果。 |

重调度器枚举待办任务顺序，并对每辆车使用最近的两个可行站点构成有限候选池。因此结果只能称为“在本次有限候选池内搜索所得的最好方案”，不能写成全局最优。论文应结合事件日志抽查具体场景，并清楚列明新增告警代表点、故障假设、通信时长样本与候选池限制。
